# [HU-24] Generar y despachar recordatorios automatizados de mantenimiento por umbrales de uso

**Dado:** Propietario de un vehículo.
**Para:** recibir recordatorios cuando el vehículo se acerque al umbral de mantenimiento.
**Que:** planificar el servicio preventivo y reducir el riesgo de averías.

**Flujo esperado**
1. El proceso programado revisa los datos de kilometraje y los intervalos de los planes activos (HU-05).
2. Identifica vehículos que alcanzan o se aproximan a un umbral de mantenimiento.
3. Genera el recordatorio y lo despacha por los canales habilitados (CI-06).
4. Registra el resultado del envío para evitar notificaciones duplicadas en el mismo ciclo.

**Criterios de aceptación**
- [ ] El recordatorio se genera con base en un umbral configurado y datos disponibles.
- [ ] El mensaje identifica el vehículo y el mantenimiento recomendado.
- [ ] No se generan duplicados injustificados para el mismo umbral y periodo.
- [ ] Los fallos de envío se registran y no se reportan como entregas exitosas.

**Endpoint:** `GET /api/v1/mantenimiento/alertas`

**Ejemplo de solicitud**
```json
{
  "query": {
    "vehiculoId": "<valor>"
  }
}
```

**Respuesta exitosa**
```json
{
  "exito": true,
  "mensaje": "Recordatorios consultados exitosamente",
  "datos": [
    {
      "alertaId": "ALR-0001",
      "vehiculoId": "VEH-0001",
      "planId": "PM-01",
      "mantenimientoRecomendado": "Cambio de aceite",
      "umbralKm": 5000,
      "estadoEnvio": "ENVIADO",
      "canal": "PUSH"
    }
  ],
  "fechaHora": "2026-10-23T12:00:00-05:00"
}
```

**Notas técnicas:** `GET /api/v1/mantenimiento/alertas` figura en la lista de APIs; la frecuencia del proceso programado y los canales (FCM/Twilio) siguen por definir. Rutas, campos y mensajes son propuesta del equipo; se confirman en el Inventario de APIs (punto 4). Los umbrales proceden de los planes de mantenimiento configurados (HU-05).

**Requisitos de pruebas**

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Vehículo alcanza el umbral | Plan PM-01 con intervalo de 5000 km; el vehículo alcanza el umbral. | Ejecutar el proceso programado y GET /api/v1/mantenimiento/alertas. | 200 OK; datos incluye una alerta con vehiculoId y mantenimientoRecomendado. |
| Kilometraje insuficiente | El vehículo no tiene lecturas de kilometraje. | Ejecutar el proceso programado y GET /api/v1/mantenimiento/alertas. | 200 OK; No se genera una alerta basada en datos inventados. |
| Recordatorio ya enviado | Existe una alerta enviada para el mismo umbral y periodo. | Ejecutar nuevamente el proceso programado. | 200 OK; No se genera un recordatorio duplicado. |
| Canal de notificación falla | El canal (CI-06) responde con error. | Ejecutar el proceso programado. | 200 OK; La alerta queda con estadoEnvio = FALLIDO para su gestión; no se reporta como entregada. |
| Consulta sin autenticación | Sin JWT. | GET /api/v1/mantenimiento/alertas. | 401 Unauthorized; exito = false; Mensaje: "No autenticado: token ausente o inválido". |

**Trazabilidad:** `MOD-06`, `FUN-17`, `PRO-17`

## Elementos comunes
### Sobre estándar de respuesta (todas las APIs)

Campos: `exito` (boolean), `mensaje` (string), `datos` (objeto, arreglo o `null`), `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP. Todas las APIs usan `Content-Type: application/json` en operaciones con body y `Authorization: Bearer <JWT>` (salvo registro, login y el webhook de la pasarela, que se autentica con su firma).
