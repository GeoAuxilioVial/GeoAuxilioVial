# [HU-03] Solicitar ampliación a rol dual

## 📖 Historia de Usuario

**Dado:** Usuario registrado.  
**Para:** solicitar un rol adicional de cliente o proveedor.  
**Que:** usar las funciones del rol adicional una vez que cumpla los requisitos y la aprobación correspondiente.

##  Flujo esperado

1. El usuario autenticado solicita el rol adicional.
2. El backend valida el rol solicitado y consulta requisitos documentales.
3. La solicitud se registra como PENDIENTE si requiere revisión.
4. Solo tras aprobar requisitos y revisión se activa el rol adicional.
5. El cambio se audita y se renueva el token o se exige iniciar sesión nuevamente.

##  Criterios de aceptación

### 1. Estructura y lógica del servicio

- [ ] No se activa rol proveedor mientras existan requisitos obligatorios pendientes o rechazados.
- [ ] Solo se admiten roles contemplados por el sistema.
- [ ] La solicitud y sus cambios de estado quedan auditados.
- [ ] El usuario no puede aprobar su propia solicitud.
- [ ] La respuesta informa estado actual y próximos pasos.

### 2. Estructura de la información y contrato JSON

Sobre estándar de respuesta para todas las APIs: `exito` (boolean), `mensaje` (string), `datos` (objeto o `null`) y `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP.

### Endpoint y método HTTP

- `POST /api/v1/usuarios/roles/solicitudes; GET /api/v1/usuarios/roles/solicitudes/{id}`
- `Content-Type: application/json` en operaciones con body.
- Autenticación: `Authorization: Bearer <JWT>` salvo registro/login.

### Ejemplo de solicitud

```json
{
  "rolSolicitado": "PROVEEDOR",
  "observacion": "Solicito habilitar perfil de proveedor"
}
```

### Respuesta exitosa de referencia

```json
{
  "exito": true,
  "mensaje": "Solicitud de rol registrada",
  "datos": {
```

##  Notas técnicas

La aprobación administrativa debe estar separada de la solicitud del usuario. Registrar auditoría del actor, fecha, estado anterior y nuevo.

##  Requisitos de pruebas

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Solicitud válida | JWT válido de usuario CLIENTE; requisitos de proveedor sin evaluar. | POST /api/v1/usuarios/roles/solicitudes con rolSolicitado=PROVEEDOR. | 201 Created; estado PENDIENTE. |
| Rol no admitido | JWT válido. | POST con rolSolicitado=SUPERADMIN. | 422 Unprocessable Entity; no se registra solicitud. |
| Sin token | No hay sesión. | POST al endpoint de solicitudes. | 401 Unauthorized. |
| Consulta de solicitud ajena | Solicitud pertenece a otro usuario. | GET /api/v1/usuarios/roles/solicitudes/rolsol_456 con token ajeno. | 403 Forbidden o 404 Not Found según política anti-enumeración; no se filtran datos. |
