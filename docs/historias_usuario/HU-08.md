# [HU-08] Registrar e iniciar sesión de usuarios con emisión de tokens JWT firmados

**Dado:** Persona que desea usar GeoAuxilio Vial.
**Para:** registrar una cuenta o autenticarme con mis credenciales.
**Que:** acceder de forma segura a las funcionalidades permitidas según mi identidad y rol.

**Flujo esperado**
1. El cliente envía los datos de registro o las credenciales al servicio de identidad.
2. El backend valida estructura, campos obligatorios y unicidad de la cuenta.
3. En el inicio de sesión, verifica las credenciales sin revelar si una cuenta existe.
4. Si la autenticación es correcta, emite un JWT firmado con identificador y roles autorizados.
5. Devuelve el resultado con el sobre JSON estándar; nunca incluye contraseña ni secretos.

**Criterios de aceptación**
- [ ] Las credenciales válidas generan un token firmado con expiración configurada.
- [ ] Credenciales inválidas no generan token.
- [ ] Correo con formato inválido o campos obligatorios ausentes se rechazan.
- [ ] El registro no permite duplicar correo o identificador único.
- [ ] La respuesta nunca incluye contraseñas ni hashes.

**Endpoint:** `POST /api/v1/auth/registro` ; `POST /api/v1/auth/login` (sin Bearer en registro/login)

**Ejemplo de solicitud**
```json
{
  "registro": {
    "nombre": "Ana Pérez",
    "correo": "ana@example.com",
    "password": "ClaveSegura123!",
    "telefono": "+573001112233"
  },
  "login": {
    "correo": "ana@example.com",
    "password": "ClaveSegura123!"
  }
}
```

**Respuesta exitosa**
```json
{
  "exito": true,
  "mensaje": "Autenticación correcta",
  "datos": {
    "usuario": {
      "id": "usr_123",
      "nombre": "Ana Pérez",
      "correo": "ana@example.com",
      "roles": [
        "CLIENTE"
      ]
    },
    "token": "<jwt-firmado>",
    "tipoToken": "Bearer",
    "expiraEn": 3600
  },
  "fechaHora": "2026-10-23T12:00:00-05:00"
}
```

**Notas técnicas:** contraseñas con hash adaptativo; JWT firmado y con expiración; límites de intentos según política del proyecto. Los códigos de autenticación y duplicidad se especifican explícitamente para este contrato.

**Requisitos de pruebas**

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Registro válido | No existe usuario con el correo enviado; endpoint disponible. | POST /api/v1/auth/registro con todos los campos requeridos y correo único. | 201 Created; exito=true; datos.usuario.id presente; no se devuelve password ni hash. |
| Credenciales incorrectas | Existe una cuenta de prueba; no hay sesión activa. | POST /api/v1/auth/login con contraseña incorrecta. | 401 Unauthorized; exito=false; datos=null; no se entrega token. |
| Payload inválido | Servicio disponible. | POST /api/v1/auth/registro con correo 'ana' o password ausente. | 422 Unprocessable Entity; mensaje de validación; la cuenta no se crea. |
| Correo duplicado | Existe una cuenta con el mismo correo. | POST /api/v1/auth/registro usando ese correo. | 409 Conflict; no se crea una segunda cuenta. |

**Trazabilidad:** `MOD-01`, `FUN-01`, `PRO-01`

---

## Elementos comunes
### Sobre estándar de respuesta (todas las APIs)

Campos: `exito` (boolean), `mensaje` (string), `datos` (objeto, arreglo o `null`), `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP. Todas las APIs usan `Content-Type: application/json` en operaciones con body y `Authorization: Bearer <JWT>` (salvo registro, login y el webhook de la pasarela, que se autentica con su firma).
