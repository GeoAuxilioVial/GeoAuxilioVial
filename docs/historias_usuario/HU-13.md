# [HU-13] Gestionar asignación y respuesta del proveedor

## Historia de Usuario

**Dado:** Proveedor elegible asignado a una solicitud.  
**Para:** aceptar o rechazar la asignación recibida.  
**Que:** confirmar rápidamente si puedo prestar el servicio y permitir la continuidad del flujo.

## Flujo esperado

1. El proveedor consulta los detalles permitidos de la asignación.
2. Envía aceptación o rechazo dentro del plazo vigente.
3. El backend valida que sea el proveedor asignado y que la asignación siga pendiente.
4. Registra la respuesta y transiciona el estado de la solicitud.
5. Si rechaza o expira, el orquestador busca el siguiente candidato según las reglas.

## Criterios de aceptación

### 1. Estructura y lógica del servicio

- [ ] Solo el proveedor asignado puede responder.
- [ ] No se aceptan respuestas después de expirar o responder previamente.
- [ ] La transición debe ser válida según máquina de estados.
- [ ] La respuesta queda auditada con fecha y proveedor.
- [ ] El rechazo no marca el servicio como completado ni pagado.

### 2. Estructura de la información y contrato JSON

Sobre estándar de respuesta para todas las APIs: `exito` (boolean), `mensaje` (string), `datos` (objeto o `null`) y `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP.

### Endpoint y método HTTP

- `POST /api/v1/auxilio/asignaciones/{asignacionId}/respuesta`
- `Content-Type: application/json` en operaciones con body.
- Autenticación: `Authorization: Bearer <JWT>` salvo registro/login.

### Ejemplo de solicitud

```json
{
  "decision": "ACEPTAR",
  "observacion": "Puedo atender"
}
```

### Respuesta exitosa de referencia

```json
{
  "exito": true,
  "mensaje": "Respuesta de asignación registrada",
  "datos": {
    "asignacionId": "asg_456",
    "decision": "ACEPTAR",
    "estadoSolicitud": "ACEPTADA"
  },
  "fechaHora": "2026-10-23T12:00:00-05:00"
}
```

El endpoint y el contrato descritos son la especificación propuesta para el proyecto; deben cotejarse con el código fuente/OpenAPI antes de declararse implementados.

## Notas técnicas

La expiración debe ejecutarse por un proceso confiable del servidor. Las transiciones deben ser atómicas para evitar respuestas concurrentes.

## Requisitos de pruebas

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Aceptación válida | Asignación pendiente y vigente; JWT del proveedor asignado. | POST /api/v1/auxilio/asignaciones/asg_456/respuesta con decision=ACEPTAR. | 200 OK; estado cambia a aceptada. |
| Proveedor diferente | JWT de proveedor no asignado. | POST al endpoint de asignación. | 403 Forbidden; estado no cambia. |
| Asignación expirada | Asignación fuera del plazo y marcada EXPIRADA. | POST con decision=ACEPTAR. | 422 Unprocessable Entity; no se acepta asignación. |
| Decisión inválida | Asignación pendiente. | POST con decision=QUIZAS. | 422 Unprocessable Entity; respuesta no registrada. |
