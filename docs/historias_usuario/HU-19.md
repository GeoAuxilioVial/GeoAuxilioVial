[HU-19] Calcular y presentar cotización estimada del auxilio en tiempo real

Dado: Cliente autenticado con vehículo registrado. Para: obtener una cotización estimada y crear la solicitud de auxilio con vehículo, ubicación y tipo de avería. Que: conocer el valor estimado con el tarifario vigente e iniciar el proceso de asistencia vial.

Flujo esperado

El cliente envía tipo de avería, vehículo, ubicación y servicio requerido.
El backend valida datos y autorización sobre el vehículo.
Consulta tarifario vigente de MOD-09/SUB-27.
Calcula el valor con reglas activas y devuelve desglose y vigencia de cotización.
No crea una solicitud confirmada hasta que el usuario ejecute el flujo de creación.
Con la cotización a la vista, el cliente confirma y envía vehículo, avería, descripción y ubicación para crear la solicitud.
El backend valida token, propiedad del vehículo y datos obligatorios.
Se registra la solicitud en el estado inicial definido por la máquina de estados.
Se dispara el proceso de búsqueda/asignación sin duplicar la solicitud.
Se devuelve el identificador y el estado inicial.

Criterios de aceptación

 Se usa el tarifario vigente en el momento de cotizar.
 El importe no es negativo y la moneda se identifica.
 Datos obligatorios ausentes o inválidos producen 422.
 La cotización no se presenta como pago confirmado.
 El vehículo debe pertenecer al cliente o estar autorizado.
 Solo se crea la solicitud si el vehículo está en estado VARADO (HU-12); en cualquier otro estado se rechaza (decisión D4).
 La ubicación debe contener coordenadas válidas.
 La solicitud se crea en un estado inicial permitido, por ejemplo PENDIENTE_ASIGNACION.
 Reintentos no deben crear duplicados si se utiliza Idempotency-Key.
 No se considera proveedor asignado hasta persistir una asignación válida.

Endpoint: POST /api/v1/auxilio/cotizaciones ; POST /api/v1/auxilio/solicitudes

Notas técnicas: la fórmula de cotización debe ser consistente con la regla de negocio y con la configuración de SUB-27. El total del ejemplo es ilustrativo. la máquina de estados es la fuente de verdad; crear, aceptar/rechazar, expirar, cancelar y cerrar son transiciones del flujo de auxilio. Esta historia se divide en dos sub-issues: HU-19.1 (calcular y presentar la cotización) y HU-19.2 (crear la solicitud de auxilio).

Requisitos de pruebas

Caso	Precondición	Acción exacta	Resultado esperado
Cotización válida	JWT válido; vehículo pertenece al usuario; tarifario activo.	POST /api/v1/auxilio/cotizaciones con payload completo.	200 OK; total numérico no negativo y moneda COP.
Falta tipo de avería	JWT válido; vehículo propio.	POST sin tipoAveria.	422 Unprocessable Entity; no devuelve cotización exitosa.
Vehículo ajeno	JWT válido de otro usuario.	POST con vehiculoId ajeno.	403 Forbidden o 404 según política.
Tarifario no disponible	Tarifario no tiene versión activa.	POST con datos válidos.	500 Internal Server Error controlado o 503 Service Unavailable si se adopta; no devuelve total ficticio.
Solicitud válida	JWT cliente; vehículo propio en estado VARADO (HU-12).	POST /api/v1/auxilio/solicitudes con payload completo.	201 Created; estado inicial válido y solicitudId presente.
Vehículo no varado	JWT cliente; vehículo propio en estado ACTIVO.	POST /api/v1/auxilio/solicitudes con payload completo.	409 Conflict; no crea solicitud.
Vehículo ajeno	JWT válido; vehículo pertenece a otro usuario.	POST con vehiculoId ajeno.	403 Forbidden o 404; no crea solicitud.
Ubicación inválida	JWT válido; latitud=200.	POST con ubicación inválida.	422 Unprocessable Entity; no se crea solicitud.
Reintento idempotente	Se envió una solicitud previamente con Idempotency-Key K1.	Repetir POST con la misma clave y mismo payload.	Devuelve el mismo recurso/identificador sin duplicar solicitud.

Trazabilidad: MOD-05, FUN-12, PRO-12

Elementos comunes
Sobre estándar de respuesta (todas las APIs)

Campos: exito (boolean), mensaje (string), datos (objeto, arreglo o null), fechaHora (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP. Todas las APIs usan Content-Type: application/json en operaciones con body y Authorization: Bearer <JWT> (salvo registro, login y el webhook de la pasarela, que se autentica con su firma).
