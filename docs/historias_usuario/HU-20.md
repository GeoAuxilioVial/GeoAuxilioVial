# [HU-20] Asignar atómicamente el proveedor disponible más cercano mediante bloqueo optimista

**Dado:** Cliente con solicitud de auxilio válida y proveedor elegible asignado.
**Para:** asignar automáticamente al proveedor elegible más cercano y gestionar su respuesta, la reasignación y la cancelación.
**Que:** recibir asistencia sin contactar manualmente a los proveedores y evitar que una solicitud quede bloqueada.

**Flujo esperado**
1. La solicitud creada entra al estado `BUSCANDO_PROVEEDOR`.
2. El sistema obtiene candidatos que cumplen disponibilidad, cobertura y frescura de ubicación (consulta de proveedores cercanos).
3. Selecciona al más cercano y confirma la asignación de forma atómica (bloqueo optimista) para evitar asignaciones incompatibles.
4. El proveedor asignado consulta la asignación y la acepta o rechaza dentro del plazo vigente; el backend valida que sea el proveedor asignado y que la asignación siga pendiente.
5. Si rechaza o no responde a tiempo, la asignación pasa a `EXPIRADA` y el orquestador busca el siguiente candidato conservando el historial.
6. Si no hay candidatos, la solicitud queda en un estado definido y se informa al cliente.
7. El cliente puede cancelar su solicitud mientras su estado lo permita; las asignaciones y procesos pendientes se detienen.

**Criterios de aceptación**
- [ ] Solo participan proveedores elegibles (RN-03, RN-05).
- [ ] La solicitud queda asociada al proveedor seleccionado y la concurrencia no genera asignaciones incompatibles.
- [ ] Solo el proveedor asignado puede responder; no se aceptan respuestas después de expirar o responder previamente.
- [ ] La transición debe ser válida según la máquina de estados y la respuesta queda auditada con fecha y proveedor.
- [ ] La reasignación se activa solo cuando vence el plazo y no existe una respuesta válida; se conserva el historial de asignaciones.
- [ ] Solo el cliente autorizado puede cancelar su solicitud y solo en estados cancelables.
- [ ] El rechazo o la cancelación no marcan el servicio como completado ni pagado.

**Endpoint:** `POST /api/v1/auxilio/solicitudes/{solicitudId}/asignacion` ; `POST /api/v1/auxilio/asignaciones/{asignacionId}/respuesta` ; `POST /api/v1/auxilio/solicitudes/{solicitudId}/reasignacion` ; `POST /api/v1/auxilio/solicitudes/{solicitudId}/cancelacion`

**Errores específicos de esta historia**

| Código | Cuándo ocurre | Mensaje (`mensaje`) |
|---|---|---|
| 409 Conflict | La solicitud no está en un estado que admita asignación o hubo conflicto de versión. | La solicitud no admite asignación en su estado actual |
| 422 Unprocessable Entity | No existen proveedores elegibles. | No hay proveedores elegibles disponibles |
| 409 Conflict | La asignación ya fue respondida o la solicitud ya no está en búsqueda. | La asignación ya no admite reasignación |
| 409 Conflict | La solicitud ya fue cancelada. | La solicitud ya fue cancelada |
| 422 Unprocessable Entity | El estado de la solicitud no es cancelable. | La solicitud no puede cancelarse en su estado actual |

**Requisitos de pruebas**

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Existe candidato elegible | Solicitud CREADA; hay proveedores disponibles, con cobertura y ubicación reciente. | POST /api/v1/auxilio/solicitudes/aux_456/asignacion. | 200 OK; estado=ASIGNADA; asignacionId y proveedorId presentes; la solicitud queda asociada al proveedor |
| No hay candidatos | Ningún proveedor cumple disponibilidad, cobertura y frescura. | POST /api/v1/auxilio/solicitudes/aux_456/asignacion. | 422 Unprocessable Entity; mensaje indica ausencia de proveedores; la solicitud permanece en BUSCANDO_PROVEEDOR según la política configurada |
| Dos solicitudes concurrentes por el mismo proveedor | Dos solicitudes buscan simultáneamente al mismo proveedor único. | POST /asignacion de aux_456 y aux_457 en paralelo. | 200 OK; solo una solicitud queda con ese proveedor; la otra continúa la búsqueda con otro candidato o permanece en BUSCANDO_PROVEEDOR; no hay doble asignación |
| Solicitud en estado no asignable | La solicitud ya está CANCELADA. | POST /api/v1/auxilio/solicitudes/aux_999/asignacion. | 409 Conflict; no se crea la asignación; el estado de la solicitud no cambia |
| Aceptación válida | Asignación pendiente y vigente; JWT del proveedor asignado. | POST /api/v1/auxilio/asignaciones/asg_456/respuesta con decision=ACEPTAR. | 200 OK; estado cambia a aceptada. |
| Proveedor diferente | JWT de proveedor no asignado. | POST al endpoint de asignación. | 403 Forbidden; estado no cambia. |
| Asignación expirada | Asignación fuera del plazo y marcada EXPIRADA. | POST con decision=ACEPTAR. | 422 Unprocessable Entity; no se acepta asignación. |
| Decisión inválida | Asignación pendiente. | POST con decision=QUIZAS. | 422 Unprocessable Entity; respuesta no registrada. |
| Proveedor no responde dentro del plazo | Asignación pendiente cuyo plazo venció. | Ejecutar el proceso de expiración / POST /api/v1/auxilio/solicitudes/aux_456/reasignacion. | 200 OK; asignación anterior EXPIRADA; se inicia la búsqueda del siguiente candidato |
| Proveedor responde a tiempo | El proveedor aceptó dentro del plazo. | Ejecutar el proceso de expiración. | 200 OK; no se ejecuta una reasignación innecesaria |
| Existe otro candidato válido | Hay otro proveedor elegible. | POST /api/v1/auxilio/solicitudes/aux_456/reasignacion. | 200 OK; se registra la nueva asignación y se conserva el historial |
| No existen candidatos | No hay proveedores elegibles. | POST /api/v1/auxilio/solicitudes/aux_456/reasignacion. | 200 OK; estado definido de la solicitud (BUSCANDO_PROVEEDOR); se informa al cliente y se conserva el historial |
| Solicitud en estado cancelable | Solicitud propia en estado cancelable. | POST /api/v1/auxilio/solicitudes/aux_456/cancelacion con causa. | 200 OK; estado=CANCELADA; se registran causa y fecha; las asignaciones pendientes se detienen |
| Solicitud en estado no cancelable | La solicitud ya está COMPLETADA. | POST /api/v1/auxilio/solicitudes/aux_900/cancelacion. | 422 Unprocessable Entity; mensaje con la razón; el estado no cambia |
| Usuario ajeno | La solicitud pertenece a otro cliente. | POST /api/v1/auxilio/solicitudes/aux_500/cancelacion. | 403 Forbidden; no se modifica la solicitud |
| Cancelación repetida | La solicitud ya fue cancelada. | POST /api/v1/auxilio/solicitudes/aux_456/cancelacion de nuevo. | 409 Conflict; no se generan efectos duplicados |

**Trazabilidad:** `MOD-05`, `FUN-13`, `PRO-13`

## Elementos comunes
### Sobre estándar de respuesta (todas las APIs)

Campos: `exito` (boolean), `mensaje` (string), `datos` (objeto, arreglo o `null`), `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP. Todas las APIs usan `Content-Type: application/json` en operaciones con body y `Authorization: Bearer <JWT>` (salvo registro, login y el webhook de la pasarela, que se autentica con su firma).
