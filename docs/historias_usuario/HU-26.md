# [HU-26] Liquidar tarifa dinámica final y procesar retención/liberación de pago al proveedor

**Dado:** Cliente que paga el servicio y proveedor del servicio.
**Para:** calcular el importe final de un servicio completado, procesar el pago mediante la pasarela Wompi y gestionar la retención y liberación al proveedor.
**Que:** aplicar la tarifa correspondiente, confirmar el estado de la transacción de forma segura y trazable y registrar la liquidación del proveedor.

**Flujo esperado**
1. El módulo recibe el servicio finalizado y los datos necesarios para liquidar.
2. El sistema consulta el tarifario vigente aplicable y calcula el valor final según las reglas definidas.
3. Se registra la liquidación con su estado para consulta y auditoría.
4. El sistema crea la intención o solicitud de pago con los datos mínimos requeridos por la pasarela.
5. El cliente completa el proceso en Wompi sin que GeoAuxilio Vial almacene datos sensibles de tarjeta.
6. Wompi envía una notificación webhook del resultado.
7. El backend verifica la autenticidad de la notificación y actualiza el estado de la transacción de forma idempotente.

**Criterios de aceptación**
- [ ] La liquidación solo procede con datos válidos del servicio y reglas tarifarias definidas.
- [ ] El cálculo no inventa recargos o factores que no estén parametrizados.
- [ ] Una solicitud duplicada no duplica la liquidación (clave de idempotencia).
- [ ] Los fallos de lectura del tarifario se registran como estados controlados, no como liquidaciones exitosas.
- [ ] La transacción queda vinculada al servicio y al identificador de pago correspondiente.
- [ ] El webhook se valida según el mecanismo de seguridad documentado por Wompi.
- [ ] Las notificaciones repetidas no duplican el pago ni sus efectos.
- [ ] El sistema no marca el pago como exitoso si la notificación no es válida o el estado reportado no confirma el pago.

**Endpoint:** `POST /api/v1/pagos/liquidaciones` ; `POST /api/v1/pagos` ; `POST /api/v1/pagos/webhook/wompi`

**Cabecera adicional:** `Idempotency-Key: <clave-unica>` (POST /api/v1/pagos/liquidaciones)

**Cabecera adicional:** `X-Event-Checksum: <checksum> (estructura de referencia; confirmar con la documentación de Wompi)` (POST /api/v1/pagos/webhook/wompi)

**Errores específicos de esta historia**

| Código | Cuándo ocurre | Mensaje (`mensaje`) |
|---|---|---|
| 401 Unauthorized | La firma del webhook no es válida. | Notificación no autenticada |

**Requisitos de pruebas**

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Servicio completado con tarifario vigente | Servicio COMPLETADO y tarifa vigente. | POST /api/v1/pagos/liquidaciones con solicitudId y kilometrosRecorridos. | 201 Created; estado=LIQUIDADA; valorFinal calculado con los parámetros vigentes |
| Datos incompletos | Sin precondiciones. | POST /api/v1/pagos/liquidaciones sin solicitudId. | 422 Unprocessable Entity; mensaje identifica el campo solicitudId; no se registra liquidación |
| Tarifario no disponible | No existe tarifa vigente. | POST /api/v1/pagos/liquidaciones con datos válidos. | 500 Internal Server Error; error controlado; no se registra una liquidación con valor inventado |
| Solicitud duplicada | Se envió antes la misma Idempotency-Key. | POST /api/v1/pagos/liquidaciones repitiendo la clave. | 200 OK; devuelve la misma liquidación; no se duplica la transacción |
| Webhook auténtico de pago aprobado | Pago pag_001 en estado PENDIENTE. | POST /api/v1/pagos/webhook/wompi con firma válida y status=APPROVED. | 200 OK; estado=CONFIRMADO |
| Webhook con verificación inválida | Pago pendiente. | POST /api/v1/pagos/webhook/wompi con firma inválida. | 401 Unauthorized; se rechaza; el pago no pasa a pagado |
| Webhook duplicado | El mismo evento ya fue procesado. | POST /api/v1/pagos/webhook/wompi repitiendo el evento. | 200 OK; se procesa de forma idempotente; no se duplican efectos |
| Pasarela informa fallo | Pago pendiente. | POST /api/v1/pagos/webhook/wompi con status=DECLINED. | 200 OK; se conserva el estado de fallo o pendiente correspondiente; no se marca como pagado |

## Elementos comunes
### Sobre estándar de respuesta (todas las APIs)

Campos: `exito` (boolean), `mensaje` (string), `datos` (objeto, arreglo o `null`), `fechaHora` (ISO 8601 con zona horaria). El cuerpo no sustituye el código HTTP. Todas las APIs usan `Content-Type: application/json` en operaciones con body y `Authorization: Bearer <JWT>` (salvo registro, login y el webhook de la pasarela, que se autentica con su firma).
