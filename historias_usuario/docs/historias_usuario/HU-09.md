# [HU-09] Gestionar vigencia documental del proveedor

## Historia de Usuario

**Dado:** Proveedor y administrador autorizado.  
**Para:** consultar y renovar documentos antes de su vencimiento.  
**Que:** mantener la habilitación operativa del proveedor cuando cumpla los requisitos legales.

## Flujo esperado

1. El proveedor consulta los documentos registrados y sus fechas de vencimiento.
2. El proveedor registra la renovación o reemplaza el documento correspondiente.
3. El backend valida metadatos, formato y vigencia declarada.
4. El proceso de revisión identifica documentos vencidos y actualiza el estado de habilitación.
5. El sistema registra auditoría y comunica el resultado.

## Criterios de aceptación

### 1. Estructura y lógica del servicio

- [ ] Los documentos obligatorios vencidos bloquean la disponibilidad operativa.
- [ ] La renovación queda pendiente hasta que la revisión requerida la apruebe.
- [ ] Solo el proveedor propietario o un administrador autorizado gestiona el documento.
- [ ] Se registra fecha de carga, vencimiento, estado y decisión de revisión.
- [ ] No se elimina el historial de documentos reemplazados.

### 2. Estructura de la información y contrato JSON

Sobre estándar: `exito` (boolean), `mensaje` (string), `datos` (objeto o `null`) y `fechaHora` (ISO 8601 con zona horaria). El código HTTP es parte del contrato.

### Endpoint y método HTTP

- `GET /api/v1/proveedores/me/documentos; POST /api/v1/proveedores/documentos; PATCH /api/v1/backoffice/proveedores/{proveedorId}/documentos/{documentoId}`
- `Content-Type: application/json` cuando exista body.
- Autenticación: `Authorization: Bearer <JWT>`.

### Ejemplo de solicitud

```json
{
  "tipoDocumento": "SOAT",
  "archivoId": "file_321",
  "fechaVencimiento": "2027-05-31"
}
```

### Respuesta exitosa de referencia

```json
{
  "exito": true,
  "mensaje": "Documento registrado para validación",
  "datos": {
    "documentoId": "doc_321",
    "tipoDocumento": "SOAT",
    "fechaVencimiento": "2027-05-31",
    "estado": "PENDIENTE_REVISION"
  },
  "fechaHora": "2026-10-23T12:00:00-05:00"
}
```

## Notas técnicas

La regla de vencimiento debe ejecutarse en backend mediante consulta y/o tarea programada idempotente. Conservar historial y auditar cambios; los archivos deben almacenarse de forma privada.

## Requisitos de pruebas

| Caso | Precondición | Acción exacta | Resultado esperado |
|---|---|---|---|
| Renovación válida | JWT de proveedor autenticado; documento próximo a vencer. | POST /api/v1/proveedores/documentos con metadatos válidos. | 201 Created; documento nuevo PENDIENTE_REVISION y documento previo conservado en historial. |
| Fecha inválida | JWT válido. | POST con fechaVencimiento anterior a la fecha actual para un documento que exige vigencia futura. | 422 Unprocessable Entity; documento no queda aprobado. |
| Consulta sin autenticación | No se envía JWT. | GET /api/v1/proveedores/me/documentos sin token. | 401 Unauthorized; no se muestran documentos. |
| Proveedor con documento vencido | Existe documento obligatorio vencido. | Consultar habilitación/disponibilidad del proveedor. | 200 OK en consulta de estado; habilitado=false o disponible=false, con motivo documentado. |
